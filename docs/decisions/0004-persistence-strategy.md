# ADR 0004: Separate domain objects from Lucid persistence

- Status: Accepted

## Context

The architecture overview states that domain code must not depend on concrete database clients and that infrastructure implements interfaces owned by the module. AdonisJS ships Lucid, an Active Record ORM: models carry persistence, relationships, hooks, and serialisation in the same class.

Using Lucid models as domain objects would be the fastest path, but it would let any caller mutate and save state without passing through invariants, couple domain tests to PostgreSQL, and expose unrestricted ORM access close to the AI tool boundary. The core invariants of the Lab — immutable stock movements, frozen BOM and routing versions on manufacturing orders, derived balances — must be protected by code that cannot be bypassed by a stray `save()`.

Read-heavy screens, traceability timelines, and experiment datasets, on the other hand, do not need rich domain objects.

## Decision

### Write side

- Aggregates, entities, and value objects are plain TypeScript classes in `app/modules/<module>/domain/`. They do not import Lucid, the database service, or any AdonisJS package.
- Each aggregate that is persisted has a repository interface owned by the module, next to the domain code.
- Repositories are implemented in `app/modules/<module>/infrastructure/` using Lucid models and explicit mappers between rows and domain objects.
- Lucid models belonging to a module live in that module's `infrastructure/` folder, not in `app/models/`. They are private to the module and are never returned by application services.
- Mutable aggregates carry a version column and repositories use optimistic concurrency checks on update.

### Transactions

- Application services own the transaction boundary through a domain-neutral unit-of-work abstraction in `app/shared/`.
- The infrastructure implementation wraps Lucid transactions; repositories and the outbox writer participate in the same transaction client.
- Domain events and outbox messages are written in the same transaction as the state change that produced them.

### Read side

- Queries do not load aggregates. Query services in `infrastructure/` may use the Lucid query builder directly and return plain, typed read models (DTOs).
- A query service only reads tables owned by its module, or projections explicitly published for it. Cross-module reads go through the owning module's query service.
- Read models are the only shape exposed to controllers, Inertia props, and AI tools.

### Ledgers and versioned definitions

- Repositories for immutable records such as stock movements expose append and read operations only, never update or delete.
- Versioned definitions such as approved BOM and routing versions are inserted as new versions; repositories do not update an approved version.

### Data types and references

- Quantities and money use PostgreSQL `numeric` columns and are mapped to a shared decimal value object, never to JavaScript `number`. The value object is backed by `big.js`: exact decimal arithmetic is all the domain needs, and the library stays replaceable behind the value object.
- Aggregate identifiers are UUIDs generated by the application, so that domain objects have identity before persistence.
- Foreign keys across module tables are allowed for referential integrity. Lucid relationships across modules are not: another module's aggregate is referenced by identifier only.

### Exception

`User` remains a Lucid model because AdonisJS authentication depends on the `withAuthFinder` mixin. It belongs to the `iam` module and is not used as a domain object by other modules; they reference users by identifier.

## Alternatives considered

- **Lucid models as domain objects.** Least code, but invariants can be bypassed, domain tests need a database, and ORM objects would leak into Inertia props and AI tools.
- **Replace Lucid with another data mapper or query builder.** Would fight the framework for migrations, authentication, and testing utilities without solving more than explicit mappers already do.

## Consequences

- Each aggregate needs a mapper and a repository, which adds code compared to plain Active Record.
- Domain invariants are unit-testable without PostgreSQL; repositories and query services are covered by database-backed tests.
- Screens and AI tools receive explicit read models, which keeps the authorised-tool boundary from ADR 0003 enforceable.
- Simple reference data may tempt contributors to skip the domain layer. That is acceptable only for modules without invariants, and the choice must stay inside the module.
